# Chapter 2 — From RAM Byte to Dot Stream: Latches, Character Generator, Shifters

*Sources: TRS-80 Technical Manual (Theory/Parts/Schematics, 1978), "Video RAMs",
"Video Processing", "Data Latch", "Character Generator", "Graphics Generator",
"Alphanumeric/Graphic Shift Register" (pp. 16–20) and Schematic Sheet 2;
cross-checked pin by pin against RetroStack's Rev G KiCad recreation
(`Video Latch.kicad_sch`, `VideoGen.kicad_sch`). Font data: xtrs `trs_chars.c`
CG 1 — see [ADR-0002](../decisions/0002-character-generator-font-data.md).
RTL: [`rtl/m1_video_gen.v`](../../rtl/m1_video_gen.v); testbench:
[`sim/tb_m1_video_gen.sv`](../../sim/tb_m1_video_gen.sv).*

Chapter 1 built the beam: a column/line/row counter marching across a 672×264 grid.
This chapter turns bytes into light. It is a two-stage pipeline — latch, then shift —
and it contains three of the Model 1's loveliest hacks: a NOR gate that fakes a
seventh RAM chip, a multiplexer that impersonates a graphics generator, and a
grounded shift-register input that *is* the spacing between characters.

## 1. Seven RAMs, eight bits: the sneaky bit (Z30)

The video RAM is seven 1-bit-wide chips: six hold character code bits VD0–VD5, the
seventh (Z63) holds the **graphic/alpha flag** VD7. Bit 6 does not exist in silicon.
Instead a NOR gate (one unit of Z30, 74LS02) computes

```
VD6 = NOR(VD5, VD7)
```

For alphanumerics (VD7 = 0) that means: codes `0x20–0x3F` (VD5 = 1) stay themselves —
digits and punctuation — while codes `0x00–0x1F` (VD5 = 0) get VD6 forced high and
become `0x40–0x5F`: the letters. The manual calls it "a sneaky way of squeezing a
seventh ASCII bit out of six RAMs". Two famous Model 1 behaviors fall out of this
one gate:

- **POKE a byte 0x00–0x1F to the screen and you see `@A B C…`** — the machine
  physically cannot address the character generator's 0x00–0x1F region (as long as
  the latches are running; see §3).
- **No lowercase.** `0x60–0x7F` would need VD6 = VD5 = 1, which the NOR can never
  produce. The famous lowercase modification is exactly this: an eighth RAM chip for
  a real bit 6, bypassing the NOR.

## 2. The data latch (Z28, Z27) — one character of pipeline

**Z28** (74LS174) captures VD0–VD5 on the rising edge of LATCH\* — the pulse chapter 1
placed once per character time. From then on the RAM is free to look up the *next*
address while the current code (now called LB0–LB5) feeds the generators. That is the
whole reason LATCH\* exists: it "delays a character between RAM and the character
generator", buying the RAM its access time.

**Z27** (74LS175) latches everything else that must stay in step with the code, and
the Rev G net names are a good map of its four flip-flops:

| D input | captured | Q/Q̅ used | meaning downstream |
|---|---|---|---|
| ¬VD7 (via Z42) | graphic flag, inverted | `~GRAPHICS` / `GRAPHICS` | which shifter loads |
| NOR(HDRV, VDRV) (Z30) | "beam is visible" | `~BLANK` | no loads in the borders |
| L8 | "in the character gap" | `~CHARGAP` (Q̅) | text blank on lines 8–11 |
| VD6 (the sneaky bit) | seventh code bit | `LB6` | chargen address MSB |

Everything the shift stage will consult is thus *delayed by exactly one character* —
data and qualifiers move together, and the blanking windows from chapter 1 arrive at
the pixel stream shifted by the same amount as the pixels themselves.

## 3. VCLR\* (Z7): why the CPU leaves black streaks

Both latches share an asynchronous clear, VCLR\*, generated by flip-flop Z7: the
moment `~VID` goes low — the CPU stealing the video RAM, chapter 3's subject — the
latches are wiped, and they stay wiped until the first LATCH\* after the CPU lets go.
A cleared latch means code 0, `~BLANK` = 0: nothing loads, the screen goes dark at
that spot. The **shift registers, however, are not cleared** (their clear pins sit on
pull-up R40) — whatever cell was in flight plays out its last ≤7 dots. That residue,
repeated every time BASIC writes to the screen, is the flickering "black streaks"
pattern every Model 1 owner knows. The testbench reproduces it: streak, darkness,
clean refill two characters after release.

## 4. The character generator (Z29, MCM6670P)

A mask ROM: 7-bit code on A0–A6 (= LB0–LB6), scan line L1/L2/L4 on its row-select
pins, five dot outputs. The glyph is 5×7, but it sits on scan lines **1–7** of the
12-line cell — row 0 reads blank, giving one empty line above the glyph and four
below (lines 8–11 are cut off by `~CHARGAP` before the chargen even matters, and
row 7 of the *stored table* is blank so line 7 shows nothing: 7 lit rows max).
The standard Tandy mask (part 8046670 / catalog 3108001; Rev G notes list all three
mask generations) differs from stock Motorola in four glyphs: `[ \ ] ^` are replaced
by **↑ ↓ ← →**, matching the keyboard's arrow keys.

## 5. The graphics "generator" (Z8) — a multiplexer wearing a costume

Block graphics need no ROM. A graphics byte's six low bits *are* the picture: a 2×3
grid of cells, each 3 dots wide and 4 scan lines tall. Z8 (74LS153, dual 4:1 mux)
merely steers them: select inputs {L8, L4} pick the cell pair for the current band —

```
lines 0–3:  LB0 (left) LB1 (right)     ← {L8,L4} = 00
lines 4–7:  LB2 (left) LB3 (right)     ← {L8,L4} = 01
lines 8–11: LB4 (left) LB5 (right)     ← {L8,L4} = 10
```

— and its two outputs each feed *three* inputs of the graphics shifter: that is how
one mux output becomes a 3-dot-wide block. There is no CHARGAP here: graphics
fill all 12 lines, which is why adjacent graphic cells fuse into solid areas.

## 6. The shift registers (Z10, Z11) and the gap that is a ground wire

Two 74LS166 parallel-in/serial-out registers, both clocked by the (inverted) dot
clock. Their eight inputs H,G,F,E,D,C,B,A shift out H-first — H is the **leftmost**
dot of the cell:

```
Z10 (text):      H=GND  G..C = chargen D4..D0   B,A = GND
                  ↑
                  the blank column between characters — a grounded pin
Z11 (graphics):  H,G,F = left cell   E,D,C = right cell   B,A = GND
```

The inter-character spacing is not computed; input H is simply wired to ground, so
every text cell starts with one dark dot. The graphics register uses H for data —
no gaps between blocks.

Loading is gated by Z26 (74LS20, two 4-input NANDs), and the conditions read like a
checklist of everything latched in §2: **text** loads require
`~BLANK · ~GRAPHICS · ~CHARGAP · LATCH`; **graphics** loads require
`~BLANK · GRAPHICS · LATCH`. A load happens during the LATCH\* pulse; the register
then shifts for one character time; serial-in is grounded, so an unloaded register
runs dry to black within a cell. Finally one more Z30 NOR unit merges the two serial
streams — only one can be loaded per cell — into the single dot signal handed to the
video mixer (analog territory, chapter "sync & mixing", later).

## 7. The pipeline, end to end

Putting chapter 1 and this chapter together, with cells numbered by the column
counter:

```
cell N   : RAM looks up address N          (address = counter)
end of N : Z28/Z27 latch code N            (LATCH* rising edge)
cell N+1 : Z29/Z8 settle on code N's dots for the current scan line
end of N+1: Z10 or Z11 loads those dots    (during LATCH*, half a dot later)
cell N+2 : the dots of character N shift out, blank column first
```

**Pixels lag the counter by exactly two character times.** The visible 64 columns
therefore occupy counter cells 2–65 — which is fine, because the borders are dark
and the monitor only sees relative timing. The testbench asserts this alignment for
every single dot of a frame.

## 8. The signal contract (what the RTL exports)

| Signal | Meaning | Hardware origin |
|---|---|---|
| `vd[5:0]`, `vd7` | the seven RAM outputs | Z61/Z62/…, Z63 |
| `vid_n` | CPU is stealing video RAM | address decoder (chapter 3) |
| `latch_n`, `dot_en`, `line`, `hdrv`, `vdrv` | from `m1_video_timing` | chapter 1 |
| `pixel` | serial dot stream, active high | ≙ ¬(Z30 pin 1) |

Inside: `lb[6:0]` (the latched code incl. sneaky bit), the font table
(`rtl/mcm6670_cg1.hex`, 128 glyphs × 8 rows, bit 0 = leftmost), and the two 8-bit
shift registers. Deviations from schematic structure (single clock, no half-dot
skew, synchronous VCLR\*) are listed in the module header; see also ADR-0001.

## 9. What the testbench proves (and how to watch it)

`sim/tb_m1_video_gen.sv` renders a full charset + block-graphics test screen and
compares **every dot of a full frame** (177 408 of them) against an independently
computed expectation — in both screen modes — then replays the CPU-steal scenario:

- text: blank column + 5 font dots, glyph on lines 1–7, dark on 0 and 8–11,
- sneaky bit: stored `0x00` renders as `@`, stored `0x3F` as `?`,
- graphics: 2×3 cells, all 12 lines, no gaps,
- pipeline: everything offset by exactly two cells against the counter,
- 32-char mode: every dot doubled, C1 pinned low → only even addresses shown,
- VCLR\*: ≤7 dots of streak, then darkness, then clean refill.

It writes `sim/build/frame64.pgm` and `frame32.pgm`; `make frames` converts them to
PNGs — the first pictures this project produces. To *see* the pipeline instead:
`cd sim && make wave-gen`, add `latch_n`, `lb`, `sr_alpha`, `sr_gfx`, `pixel` next
to `col`, zoom to ~3 µs and watch a code enter `lb`, surface in `sr_alpha` one cell
later, and leak out of `pixel` bit by bit. The famous streaks are at the `vid_n` dip
(~33 ms): `lb` snaps to zero while `sr_alpha` keeps draining.
